Why ryzek exists

The trust model broke before
anyone noticed.

Agent skills went from a novelty to a supply chain in about a year. The review process didn't come with them.

The problem, plainly

An agent skill is a file that tells an AI agent how to do something. It ships with permissions — filesystem, network, sometimes credentials — and when installed, it runs with everything the agent itself can reach.

People install them the way they install an npm package: quickly, from a link someone shared, without reading the contents. That was survivable when a package could only run code. It is a different proposition when the thing being installed can also instruct the agent — quietly, in text a human never sees.

A package can run code. A skill can change what the agent believes it was asked to do.

That distinction is the whole reason this tool exists. Classic security scanning asks whether code does something dangerous. Agent skills need a second question: is anything in here talking to the model instead of to me?

Who builds this

Ryzek is built and maintained by the ryzek team — a small, independent group working on this and nothing else.

The project started from a straightforward observation. Software is increasingly not run by people. It is run by agents, on behalf of people, at machine speed, across systems nobody fully inventories. That shift is happening whether or not the safety tooling keeps up — and right now it isn't keeping up. The incidents above are what that gap looks like in practice: not exotic zero-days, but ordinary mistakes that used to be recoverable and now execute automatically before anyone reads them.

Ryzek exists to put a checkpoint in front of that. Not to slow anything down — the whole thing runs in about a second — but to make sure the small number of things that genuinely shouldn't run, don't.

What being independent means in your favour: a fix can ship the day a problem is found. There is no roadmap committee deciding whether agent-skill security is a big enough segment this quarter. Every rule in the tool exists because it was worth writing, not because it filled a comparison table.

What it means against: there is no large support organisation behind this, and no formal SLA on the standard plans. For a team evaluating ryzek against a heavily funded vendor, that is a real difference, and it should be weighed rather than glossed over. It is also why the source is public — you do not have to take our word for how any of it works.

How it's built, and why those choices

Local by default

Nothing you scan leaves your machine. Most tools in this space require an API token and send your files to a hosted service — which is a strange thing to accept from a tool whose job is telling you whether those files are trustworthy.

Every finding states its reasoning

A confidence score and a plain-language reason on every result. Untuned scanners routinely produce 60–90% false positives, and people who learn to ignore false findings also ignore real ones.

Fixes are computed, not generated

Where a fix is offered, it was derived from the finding, not predicted by a model. Fixes that need human judgement say so instead of guessing — a wrong security fix closes the ticket while leaving the hole open.

Detection isn't paywalled

Every rule runs in the free tier. Paid plans buy scale, not capability. A security tool nobody can verify for free is a security tool nobody has reason to trust.

This isn't hypothetical

Every case below is documented and publicly reported. For each one, the honest question isn't "would ryzek have stopped this" — it's which part of it ryzek can see, and which part it can't. Both are stated.

Secrets sitting in agent config files

GitGuardian's 2026 State of Secrets Sprawl found 24,008 secrets in MCP-related configuration files on public GitHub — 2,117 of them still valid. Live credentials, committed to public repositories, inside the config files that tell agents how to connect to things.

What ryzek does: this is exactly what the mcp-credential-in-config rule catches, and it's the clearest case on this page. It flags a literal secret sitting in a config value, tells you which key, and gives you the fix — swap it for an environment reference. It also correctly ignores ${VAR} references, so it doesn't cry wolf on configs that already do this properly. Run before you commit, this class of leak doesn't happen.

The Postmark MCP backdoor

In September 2025, a compromised npm package called postmark-mcp was found to be silently BCC-ing every email that passed through it to an attacker-controlled address. It ran for over a week, forwarding an estimated 3,000 to 15,000 corporate emails per day — password resets, invoices, internal communications, customer data.

What made it effective is worth sitting with: email gateways didn't flag the BCC because it looked like legitimate Postmark API traffic. DLP never inspected the call body. And static scanning didn't flag the one-line change, because the diff looked benign and the package had a clean version history.

What ryzek does: partially. It would not have identified that single line as malicious — that's the same limitation the report describes, and claiming otherwise would be dishonest. What it does catch is that the package changed after you approved it. Drift detection compares against a baseline you set, so a silently updated dependency raises a flag that says "this is not what you reviewed" — which is the moment a human looks. That's a meaningfully different claim from "we'd have detected the backdoor," and it's the accurate one.

The STDIO configuration flaw

In April 2026, OX Security disclosed a systemic flaw in the STDIO transport used by every official MCP SDK — Python, TypeScript, Java, and Rust. Configuration values flow directly into command execution, meaning any input reaching a server's startup config becomes an arbitrary OS command. They traced ten resulting CVEs across LiteLLM, LangChain, LangFlow, Flowise and others, totalling over 150 million combined downloads.

Anthropic reviewed it and declined to change the protocol, taking the position that sanitisation is the downstream developer's responsibility. So it isn't getting patched upstream. It's a live, acknowledged exposure that every affected developer now owns individually.

What ryzek does: checks for it directly, and grades honestly. A literal command gets an informational note. Interpolated values or shell metacharacters get flagged as an actual injection path. The npx -c form gets marked critical, because that's the exact pattern researchers used to bypass one vendor's command allowlist in a single step. As far as we can tell, no other scanner checks for this at all.

The trojanized Oura Ring server

In February 2026, a malware operation spent three months building a fake developer ecosystem — five GitHub accounts with AI-generated personas, cross-forked to simulate an active community — before submitting a trojanized MCP server to a legitimate registry. The fork was functionally identical to the real thing. The payload silently exfiltrated browser passwords, cloud session tokens, SSH keys, and cryptocurrency wallet files.

What ryzek does: partially, and it depends. Ryzek reads what a server's configuration and bundled code actually do, not who published it or how many stars the repo has — so a payload that reads credentials and sends them outbound trips the credential and network rules regardless of how convincing the surrounding ecosystem looked. What ryzek cannot do is tell you a maintainer is fake. Reputation isn't something static analysis can assess.

The Asana cross-tenant leak

In June 2025, a logic flaw in Asana's MCP server exposed customer data across organisations for roughly two weeks.

What ryzek does: nothing, and it's worth saying so plainly. This was a bug inside someone else's hosted service. No local scanner can see it. The only thing that limits damage in that situation is how much access each connected agent had in the first place — and ryzek does flag permissions broader than a tool's stated function needs. That caps a blast radius; it doesn't prevent the incident. Anyone telling you their scanner would have stopped this is selling you something.

A tool that claims to catch everything is a tool you can't calibrate against. Knowing precisely where ryzek stops is what makes the rest of it usable.

The scale underneath all of this

Snyk's audit of 3,984 agent skills found 13.4% contained at least one critical security issue. Antiy CERT confirmed 1,184 malicious skills in one agent ecosystem alone. Trend Micro found 492 MCP servers exposed to the open internet with zero authentication. And in a 2026 industry survey, 88% of organisations reported a confirmed or suspected AI agent incident in the previous year.

Meanwhile only around a quarter of enterprises have any dedicated AI security governance at all. The tooling gap isn't a prediction — it's the current state.

Where this is going

The attack surface is expanding faster than the tooling around it. Three things are already visible:

Shipped
Skills, MCP configs, and config files
Detection across the three artefact types agents actually load, including the MCP STDIO configuration flaw disclosed in April 2026 — a by-design behaviour the protocol maintainers have declined to change, leaving remediation to individual developers.
Next
Composition and multimodal
Two skills that are individually harmless can form an exfiltration path together — no per-file scanner can see that. And instructions are now being hidden inside images referenced by skills, defeating text-only analysis entirely.
After
Distribution and depth
Standalone binaries with no runtime dependency, editor integration so problems surface before installation rather than after, and a desktop application for people who would rather not live in a terminal.

The longer bet

Right now, most agent-security tooling is given away as a lead-in to a larger platform. That works for companies with a larger platform to sell. It also means the tools themselves get exactly as much attention as their role as a funnel justifies.

Ryzek isn't a funnel. It's the product. The bet is that a tool built by a team whose only job is making that tool good ends up better than one maintained as a marketing expense — and that a growing number of people would rather pay a small amount for something focused than use something free that treats them as a lead.

That's the thesis. It's testable, and it's being tested now.
